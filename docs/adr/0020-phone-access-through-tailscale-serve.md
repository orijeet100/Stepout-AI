# 0020 — The phone reaches the laptop through Tailscale Serve, and only its owner gets in

Status: accepted · 2026-10-12 · built and tested against a fake `tailscale`; first run on a real tailnet 2026-10-12; amended by [0021](0021-start-repairs-itself.md) (neutral generated name, Serve checked before the link is announced, no Serve reset).

**Decision.** `stepout remote` gives the laptop's chat an HTTPS name reachable only by the owner's own devices, with **Tailscale Serve**: free, no domain, no server of ours, no account of ours. Not Funnel (the public internet), not a hosted hub. The server still listens on `127.0.0.1` only; Serve connects to it locally (`tailscale serve --bg --https=443 http://127.0.0.1:<port>`; `stepout remote off` undoes it).

**The guard.** `stepout remote` writes two lines to Home's `.env`: the exact host name (`STEPOUT_REMOTE_HOSTS`, no wildcards) and the owner's Tailscale login (`STEPOUT_REMOTE_LOGIN`, from `tailscale status --json`). The web channel then also accepts `Host: <name>` and `Origin: https://<name>`, and any request that arrived from another device (its Host is the remote name, or it carries `Tailscale-User-Login`, `X-Forwarded-For` or `X-Forwarded-Host`) must carry the owner's login in `Tailscale-User-Login`, or it gets 403. Serve sets that header and removes any copy a client sent; it sends none for tagged devices or Funnel, so those are refused. This is a second layer because a tailnet can hold more than one person. Requests straight to `127.0.0.1` behave as before.

**Why the forwarding headers count.** Whether Serve keeps the original `Host` is not documented. If it rewrote it to `127.0.0.1:<port>`, a request from a tagged device would look local; treating any forwarded request as remote closes that.

**The rest.** Each step of `stepout remote` prints only the next action and waits (install with `winget install Tailscale.Tailscale` (exact case: see the update below), sign in, choose a neutral name, since HTTPS names land in a public certificate log), then prints the URL and a QR code (`segno`, no dependencies) and starts the chat. While phone access is set up, the app keeps Windows from idle sleep (`SetThreadExecutionState`; a closed lid still sleeps). Grants never change from a phone or a page (0019). The page shows the laptop's name (`hello.machine`) and can be added to a home screen (a web manifest).

**Limits.** Windows only. The real Serve flow was first checked only against Tailscale's docs and a fake CLI; it has since been run on a real tailnet (see the update below). The phone needs the Tailscale app signed in to the same account. A sleeping laptop is unreachable; there is no queue.

**Update, 2026-10-16.** Run on a real tailnet (one Windows laptop, an iPhone). *First use:* `tailscale serve --bg --https=443 http://127.0.0.1:<port>` prints "Serve is not enabled on your tailnet. To enable, visit: <link>" and waits until the link is followed once. *What Serve sends the backend* (a throwaway echo server behind a handler on HTTPS port 8443, removed afterwards; the 443 handler was not touched): the original `Host` is kept (on 8443 with its port), and `Tailscale-User-Login`, `Tailscale-User-Name`, `Tailscale-User-Profile-Pic`, `Tailscale-Headers-Info`, `X-Forwarded-For`, `X-Forwarded-Host` and `X-Forwarded-Proto` are added. So the open question above is answered: Serve keeps the `Host`. The rule that any forwarded request needs the owner's login stays as a second layer for a case Serve does not produce today, because Serve's behaviour is not a promise we hold. *The winget id* is `Tailscale.Tailscale`: with `-e` winget finds nothing for the lower-case form this ADR first gave, so the first version of the offered install would have found no package. It was fixed on this date; the install itself has still not been run on a machine without Tailscale.
