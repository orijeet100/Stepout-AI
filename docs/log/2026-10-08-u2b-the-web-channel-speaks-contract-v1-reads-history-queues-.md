**What.** `channels/web.py` is rewritten for UI contract v1. Every frame and API body is built from the models in `contract.py`, so the channel cannot drift from the contract. Over `/ws`: `hello` then `status` on connect; your `send` is echoed as a `message`; each Runner event is a `trace` frame (same id as its Ledger row); each reply is a `message` with `run_id` and `cost_usd`; `status` follows the queue (`state`, `active` with the run id and the Run's cap once its first event arrives, `queued`). Over HTTP: `GET /api/conversations`, `POST /api/conversations` (201, a server-made id), `GET /api/conversations/{id}`, `GET /api/runs/{id}/events`, `/shots/...`, all read through a small `HistoryReader` interface; `StoreHistory` wires it to `history.py`. **Queue:** the channel is the inbox. A message sent while a Run is busy waits in order, shows as `queued` in `status` and in the chat list, and is added to its chat when read back (it is not saved until its turn). A chat whose first message is still queued is listed. The old v0 inbound frames (`{"text": …}`, `{"stop": true}`) are still accepted, into the default chat, for one release; v0 frames are no longer sent.

**Security** (each rule has a test, and each test fails when its rule is switched off): `Host` must be `127.0.0.1:<port>` or `localhost:<port>` on every route; a present `Origin` must be ours; a POST needs an `Origin` and `application/json`; ids are 32 hex (plus the literal `default`) and checked before any lookup, and `send` only accepts a chat the database knows or this process issued; frames are validated by `contract.py` (`extra="forbid"`), capped at 64 KB and 20 000 characters; no CORS header is ever sent, errors included.

**Page changes that U2b needed.** History is the record: when a chat is read back, only live messages newer than anything history has are kept (a live user message and its saved copy have different ids until Main carries ids through). The reconnect banner no longer flickers between "Disconnected" and "Connecting…".

**Why.** U2b of the plan, and X2: the page must work against the real backend. Before this the real server answered `GET /api/conversations` with 404 and `POST` with 405, so no message could be sent from the page.

**Alternatives.** Dropping v0 inbound now (the plan says one release). Emitting a status per Runner event (only the first event of a Run changes it). Reading the cap from the environment instead of the Run row (the row is the truth, and B2 added it for this).

**Evidence.** `python -m pytest -q`: **180 passed**, 6 deselected (the 7 old channel tests became 18); `tests/test_contract.py` validates all seven fixtures. `npm test`: 36 passed; `python -m pytest web/mock -q`: 9 passed. The last channel test runs the real app loop (SavedChannel, Intake, Runner, Ledger, the SQLite Store, history.py) with a scripted model behind the real channel: every frame is valid against `contract.py`, history returns the same event ids in the same order, and the live reply and the saved one are the same message. **Against the real backend** (`python web/mock/real_backend.py`, the same wiring as `python -m stepout.app web`, only the model and the browser scripted; costs nothing): the built page served by the channel itself created a chat on first send, streamed a Run, showed plan and steps and cost, Stop ended a Run ("Stopped by you."), a declined request showed no run, a reload and a backend restart brought the whole chat back from SQLite and the page reconnected by itself, and a message sent in a second chat during a Run showed as queued and ran next. That check found a bug the tests had missed (a reply showed twice after a history reload: the saved copy is written before the live frame); the channel now sends the saved copy's id and time, and the integration test pins it. The real entry point `python -m stepout.app web` (dummy key, no message sent) answers `GET /api/conversations` 200, `POST` 201, a non-JSON POST 415, and opens the socket with `hello` and `status`. **Not verified:** a real model and real Chrome (a paid run: the merge agent's `-m eval` step, after telling the User the cost).
