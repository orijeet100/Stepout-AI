**What.** Cycle C2, slice 2 of the Reader ([plan](../plan/v0-finish.md)): the first time the Assistant reads file *contents*. A new capability `read_text` (one file, one line in `ALL`) over a new hand, `src/stepout/reader.py`. Not yet held by any Role (the Reader Role is slice 3) and not yet closing the web after a read (strict taint is slice 4).
1. **Path.** `Files.resolve_readable(raw)`: the same `_resolve` as the `files` tool (a plain absolute local path, real path with links and 8.3 names resolved, the fixed block list, the grants), so a bad path is refused **in the same words** (tested for eight kinds of bad path). It adds two rules: the path must lie under a grant in **`read` mode** (a `metadata` grant allows names, sizes and counts only; `_resolve` ignored the mode until now), and it must be a file.
2. **Kind by content.** `%PDF-` at the start means PDF; otherwise the bytes must decode as text (UTF-8, a UTF-8 or UTF-16 byte order mark, or Windows-1252 as a fallback) and not look binary (a NUL in the first 8 KB, or more than 10% odd characters). A name proves nothing: a `.pdf` that is text is read as text, a `.txt` that is a PDF as a PDF, an executable named `.txt` is refused.
3. **PDF** through pypdf 6.19.0 (BSD-3-Clause, read from the package's metadata; added to `pyproject.toml` and `docs/third-party.md`). Encrypted without an empty password: "needs a password", not opened. A PDF with no text (scans): reported, "no OCR, do not guess", **no content returned**. A malformed one: "could not be read as a PDF". Extraction stops once about 41,000 characters are in hand, at most 200 pages are read, and a page whose decompressed content is over 5 MB is skipped (the pypdf docs warn that extraction needs memory for the whole content stream).
4. **Limits per Run** (kept in `RunState`, shared by every Role of the Run): **20 files** and **10 MB in all** (I read the plan's "10 MB" as the Run's total, the stricter reading; a file that does not fit in what is left is refused before it is opened), and **40,000 characters per file sent on**. Whatever was cut is said: "the first 40,000 of 100,000 characters are shown; the rest was not sent", or, when a long PDF stopped early, "the first 40,000 characters are shown; the rest was not read" (the true length is then unknown, so no number is invented).
5. **Before a model sees the text:** control, zero-width and bidirectional-override characters are removed; secrets are replaced by `[redacted]` and counted ([decision](2026-10-08-secret-screening-is-by-patterns-before-the-model-sees-file-te.md)). The text is screened as a whole window before the cut, so a key that crosses the 40,000 mark is not left half visible.
6. **The read runs in a worker thread with a 30 second limit**, so a hostile file can spoil one read but not freeze the Assistant or Stop. After the open, the real path is checked again; if the file was swapped for a link between the check and the open, it is refused.

**Why.** The Reader (M4) is the last V0 capability; its demos are "summarize the newest PDF" and "compare my resume to a job posting". Everything risky is in one hand so the capability stays a thin wrapper, and the paths are the existing resolver's, so the file tool and the reader cannot disagree about what is allowed.

**Threat model, in a few lines.** The path is written by the model (refused by the resolver; tests for relative, `..`, outside a grant, blocked name, blocked folder, missing, network path, alternate stream, and a junction or symlink into the block list or out of the grant). The contents are written by anyone and may carry instructions (data, never instructions; secrets screened; and the web will close after a read, slice 4). The PDF can be built to be expensive (size budget, page cap, per-page size check, character window, thread and time limit; a 6 MB page packed into a few KB is skipped).

**What I could not verify.** The pypdf page that should document tightening its resource limits (`pypdf.Configuration`) returned a 404, so the library's own defaults apply (75 MB per decompressed stream): **unverified** how to lower them per reader. A very large real-world PDF and the CPU a pathological one costs: the thread cannot be killed on a timeout (a `ponytail:` note in `reader.py`; the fix is a subprocess).

**Alternatives.** OCR for scans: out of V0. A third-party PDF tool or `pdfminer`: another dependency for the same job. Reading by extension: rejected, see 2. Truncating before screening: rejected, see 5.

**Evidence.** Offline suite **328 passed, 7 deselected** (295 before; +33 in `tests/test_reader.py`, plus the Action round trip now includes `ReadTextAction`). The PDFs are made in the test by `tests/support/pdfs.py` (a generator that even pypdf's strict parser accepts; encrypted ones via pypdf) and read by the real pypdf, and the files are real files under `tmp_path`, behind real grants. The security tests were mutated to prove they can fail: ignoring the grant mode, removing the secret screening and removing the swapped-file guard each break exactly the tests meant to catch them (the swap guard had **no test** until the mutation showed it; it has one now).
