**What.** Cycle C1, task 2 of [the V0 finish plan](../plan/v0-finish.md): the Main half of [the live-view seam](2026-10-08-live-view-get-live-run-id-and-the-browser-on-frame-seam.md), built as the contract's "Live view" section says. No wire shape changed.
1. **`Browser(shots=…, on_frame=cb)`**, `cb(run_id: str, jpeg: bytes) -> None`. Synchronous, called from the event loop, so it must not block (the web channel just keeps the newest frame per Run). **At most four calls a second per Run** (a gap of 0.26 s between two frames of one Run, so four in any second; five would need 1.04 s). JPEG at quality 50, no larger than the 1000×700 viewport. Started when a Run's page is created, **before** its first page opens (so the load is seen), and stopped when the Run's browser closes (`close`/`aclose`). **No callback means no capture**: the screencast is never started.
2. **A callback that raises never breaks a browse action.** Everything the callback does is inside `try/except`; the first error per Run is logged as a warning, later ones are not. This matters: with Playwright 1.63 and the installed Chrome, an exception escaping a screencast callback **does** surface in the Run's next page call (`Page.title: boom`; probed), so it would have broken the action. If starting the screencast fails, it is logged and browsing goes on without frames.
3. **The limiter keeps the newest frame** and sends it as soon as the gap allows, instead of dropping a frame that arrives too soon. Plain dropping would lose the last frame of a page that then stays still (typical right after a click) and the viewer would show a stale page until something changed. The four-a-second cap still holds because every send goes through the same gate; a timer that fires a hair early waits again.
4. **`app.py`**: `make_browser(channel)` passes `getattr(channel, "live_frame", None)` as `on_frame`. The web channel (the UI lane's, not touched here) will have a `live_frame`; the terminal has none, so it captures nothing.
5. **`pyproject.toml`: `playwright>=1.59`** (was 1.49). `page.screencast` was added in 1.59; before that the call fails (safely, by item 2, but without frames). The installed version is 1.63.

**How frames are taken, from the official Playwright Python docs (`page.screencast`, read 2026-10-08) plus a probe, since the docs leave things open.** The docs say `start(on_frame=…, quality=…, size=…)` delivers "JPEG-encoded frames" as a dict with `data`, `timestamp`, `viewportWidth`, `viewportHeight`; `size` is a maximum (default: the viewport scaled into 800×800, so `size` is set explicitly to 1000×700); `stop()` ends it. They do not say whether the callback may be synchronous, what happens if it raises, or the rate. The probe against real Chrome: a plain function works (so does a coroutine function); an animated page gives about 23 frames a second; frames arrive during a load and after a click and stop after `stop()`; an exception in the callback breaks the next page call. Raw CDP (`Page.startScreencast`, with `everyNthFrame` and per-frame acks) was not needed.

**Shortcut with a ceiling** (marked `ponytail:` in `browser.py`). Chrome encodes about 25 frames a second on an animated page and we keep four, so most are encoded for nothing. Ceiling: CPU while a page animates. The fix, if it ever matters, is raw CDP with `everyNthFrame`.

**Alternatives.** Raw CDP now: more code (acks, a session per page) for no gain until the CPU shows. Plain dropping (no newest-frame hold): simpler, but the stale-final-frame problem above. Capturing screenshots on a timer: a screenshot per step already exists; a timer would cost as much CPU and stutter.

**What I could not check.** The route and the page (UI lane's, not built yet): no frame has been seen by a person. How hard an animated page loads the CPU, and memory over a long Run (the limiter holds at most one frame per Run). That the merge agent's live check on a real page shows a smooth view at four frames a second.

**Evidence.** Offline suite **264 passed, 7 deselected** (252 before; +12). `tests/test_live_frames.py` (no Chrome, a fake screencast, precise timing): the screencast starts with quality 50 and the 1000×700 size; a burst of ten frames sends the first at once and, after the gap, only the newest; a 50-frames-a-second stream for 1.4 s never has two frames closer than the gap or more than four in any second and ends on the last frame fed; a raising callback is called again each time it is allowed, never raises into Playwright, and is logged once; a frame without `data` is ignored; closing stops the screencast and cancels the waiting frame, and a late frame goes nowhere; a failed start does not stop browsing or the close. `tests/test_browser.py` (real Chrome): frames arrive while a page loads and after a click and are JPEGs no larger than 1000×700; two Runs on an animated page each stay within four in any second and ≥ 0.25 s apart; a raising callback leaves `open`, `click`, `more` and the screenshots working and logs once; without a callback `framing` is false, with one it is true and no frame arrives after the Run closes. `tests/test_app.py`: `make_browser` hands the channel's own `live_frame` through and gives `None` for the terminal. The two timing files were run three times in a row (15 passed each time); with the gap patched to 0 the rate test fails, so it does detect a missing cap. By hand: the real terminal app starts with the new wiring. Files: `src/stepout/{browser,app}.py`, `pyproject.toml`, `tests/{test_live_frames,test_browser,test_app}.py`.
